# How to help build Omnissiah

There are three ways to help, from one click to writing code. You need a free GitHub account for all of them.

| I want to... | Do this | Time |
|---|---|---|
| Say what should be built next | [Vote on an idea](#1-vote) | 10 seconds |
| Suggest something new | [Propose an idea](#2-propose-an-idea) | 2 minutes |
| Build something | [Pick a task and send a pull request](#3-build-something) | an evening or more |

## How the project runs: the schedule

The project is maintained by its owner together with Claude, an AI assistant. Claude does the routine reviewing on a fixed schedule:

| What | How often | What happens |
|---|---|---|
| **Pull request review** | every 15 minutes | Every open pull request that has new commits is read. If it is a good implementation of a task from [IMPROVEMENTS.md](IMPROVEMENTS.md) (or another clear improvement), it is **approved**. If not, the review **asks for a rewrite** and says exactly what to change. |
| **Idea review** | every 24 hours | The ideas in Discussions are read, most-voted first. Accepted ideas become tasks in [IMPROVEMENTS.md](IMPROVEMENTS.md); the rest get a reply explaining why not. |
| **Merging** | when the owner is around | Approved pull requests are merged by the owner. Changes to the server, start scripts, dependencies or the AI prompts always need the owner's own approval first. |

Two honest limits: the schedule runs on the owner's PC, so it pauses when that machine is off (reviews then happen when it
is back); and the reviewer reads your change but does not run code from pull requests on that PC, so say clearly how
**you** tested it.

## 1. Vote

1. Open [Discussions → Ideas](https://github.com/TengilOurLiberator/omnissiah/discussions/categories/ideas).
2. Open an idea and press the **up arrow** next to its title.

Votes decide what is looked at first in the daily idea review. Details: [VOTING.md](VOTING.md).

## 2. Propose an idea

1. In [Discussions → Ideas](https://github.com/TengilOurLiberator/omnissiah/discussions/categories/ideas) press **New discussion**.
2. One idea per post. Describe what a player would see or do, e.g. "fish off the jetty and cook the catch at the fire".
3. Within a day or so (sooner if it gets votes) it gets a reply: accepted and added to the task list, or declined with reasons.

Found a bug instead? Open an [issue](https://github.com/TengilOurLiberator/omnissiah/issues) with what you did, what happened, and browser/headset.

## 3. Build something

You can write the code yourself or direct an AI coding agent (Claude Code, or any other) to do it; the task list is written for both.

1. **Get the game running:** follow [GETTING_STARTED.md](GETTING_STARTED.md). You do not need a headset; it runs flat in Chrome or Edge.
2. **Pick one task** from [IMPROVEMENTS.md](IMPROVEMENTS.md). Each says why it matters, which files to look at, and what "done" means.
   Small ones marked **(S)** are good first tasks. To avoid two people doing the same thing, comment on the matching idea in Discussions that you are on it.
3. **Fork** the repository on GitHub, clone your fork, and make a branch.
4. **Make the change.** If you use an AI agent, give it the task text and tell it to read the "Before you start" section of
   IMPROVEMENTS.md first; that section holds the rules that keep the game stable (clean-up on reload, performance budgets, how to verify).
5. **Test it yourself:**
   - the game boots with no errors in the browser console (`start.bat`, then `http://localhost:8080`);
   - the opening still plays (or **Esc** skips it cleanly);
   - `node tests/run.mjs` passes;
   - for anything visual, take before and after screenshots, on `?quality=pc` and `?quality=quest`.
6. **Open a pull request** to `main` and fill in the template: what a player will notice, how you tested, what you could not test.
7. **Wait for the review** (normally within 15 minutes while the maintainer's machine is on). You get one of:
   - **Approved** — it is a good implementation; the owner merges it.
   - **Changes requested** — the review lists what to rewrite. Push new commits to the same branch; it is reviewed again automatically.
   - **Needs the owner** — it touches the server, scripts, dependencies or AI prompts; the owner decides.

### What gets approved

- It does what the task's "Done when" says, or is another improvement a player would notice.
- It is one focused change, not a bundle.
- It follows the module rules (hot reload safe, cleans up, nothing heavy per frame, Quest budget respected).
- Scenery uses the hand-painted generated set (`world.gen`), not coloured boxes.
- You explain how you tested it, and you are honest about what you did not test.
- Assets are your own, generated by you, or clearly licensed for reuse.

### What gets sent back

- It does not do what it claims, breaks the boot or the opening, or the description does not match the code.
- No evidence of testing, or the screenshots show a problem.
- It mixes several unrelated changes, or rewrites working code for no visible gain.
- It adds paid services, tracking, secrets, or assets without a usable licence. Those are declined outright.

The full policy is short: [CONTRIBUTING.md](../CONTRIBUTING.md). Everything you contribute is released into the public domain like the rest of the project ([LICENSE](../LICENSE)).
